# 文档组织与开发流程

本文规定项目文档的职责、阶段交付方式和开发审核流程。开发代理负责设计、实现和自动验证，用户负责关键文档审核及应用体验验收。Git 操作遵循 [AGENTS.md](../AGENTS.md)。

## 1 文档组织原则

采用“长期规范 + 阶段交付文档”的结构。长期规范维护当前有效规则；阶段文档记录各阶段的实施安排、验收步骤和交付结果。

- 同一规则只有一个维护位置，其他文档通过相对链接、章节或需求编号引用。
- 不复制产品规则、接口定义、页面规格或验收标准到阶段文档。
- 每个阶段只维护一份文档，阶段内的设计、任务、测试和结果集中记录。
- 按阶段需要创建文档，不提前生成大量空文件；不另外建立重复的阶段报告或验收汇总。
- 明确区分已确认规则、待审核方案、待验证技术候选和实际验证结果。
- 文档写当前结论；讨论过程和已放弃方案仅在有助于理解最终取舍时保留。

## 2 文档职责

| 文档 | 唯一维护的内容 |
| --- | --- |
| [README.md](../README.md) | 项目简介、当前状态、文档导航与阅读关系 |
| [PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md) | 产品目标、业务规则、范围与已确认决策 |
| [CORE_ENGINE.md](CORE_ENGINE.md) | 比对规范、语言模块、数据结构、接口和状态契约 |
| [WEB_UX.md](WEB_UX.md) | 页面布局、用户操作、反馈和交互规则 |
| [WEB_LOCAL_PROCESSING.md](WEB_LOCAL_PROCESSING.md) | 浏览器能力、识别模型、资源管理和静态部署约束 |
| [DELIVERY_PLAN.md](DELIVERY_PLAN.md) | 整体交付顺序、阶段范围、依赖、进度及长期验收标准的索引 |
| DEVELOPMENT.md（按需建立） | 技术栈、工程结构、环境要求、开发命令和测试方法 |
| stages/ 下的阶段文档（按需建立） | 本阶段实施安排、用户验收步骤、实际验证结果与交付记录 |
| [AGENTS.md](../AGENTS.md) | 开发代理协作约束和 Git 规则 |

现有 A 类验收标准及核心性能目标仍在 DELIVERY_PLAN.md，B 类验收标准仍在 WEB_LOCAL_PROCESSING.md。阶段文档引用对应编号，补充可执行的操作步骤和实际结果，不重新定义标准。

文档存放于 doc/，阶段文档存放于 doc/stages/，文件名采用“顺序编号 + 简短英文主题”。工程开发指南与本文分开：前者说明如何运行和维护代码，本文说明如何组织和交付工作。

## 3 阶段文档结构

每份阶段文档使用以下结构，随着工作推进更新同一文件。

| 部分 | 必须记录的内容 |
| --- | --- |
| 状态与范围 | 当前状态、交付目标、范围边界、前置条件、所依据的规范链接及需求编号 |
| 实施安排 | 工作拆分、执行顺序、依赖和本阶段特有的实现选择；涉及长期契约的设计链接到对应规范 |
| 用户验收 | 测试环境、必要材料、准备条件、操作步骤和可观察的预期结果 |
| 交付记录 | 实际实现范围、自动验证结果、用户验收结论、对应提交和未解决问题 |

状态依次为：待审核、开发中、待用户验收、修正中、已完成。存在阻塞时注明原因及受影响任务；未实际执行的验证标为未执行，不写为通过。

## 4 整体开发流程

### 4.1 明确范围与准备文档

开发代理结合交付计划和当前规范，确定阶段目标、依赖及完成条件，创建或更新阶段文档。若已有规则发生变化，先修改其所属长期规范，再在阶段文档中引用。

准备方案时明确需要用户决定的问题，并给出建议及取舍。常规实现细节由开发代理处理，不要求用户逐项审核代码组织或内部实现。

### 4.2 用户审核

开发代理提供当前阶段文档和本次有变化的规范章节，说明需要审核的范围。用户重点确认产品行为、阶段边界、重要技术选择和验收预期。

设计确认后进入实现。文件编辑完成后的提交询问按 AGENTS.md 执行；设计审核、Git 提交授权和应用验收分别记录，不互相替代。

### 4.3 实现与自动验证

开发代理按已确认范围完成代码、必要测试及文档维护，执行适合改动的构建、静态检查和自动测试。测试优先覆盖业务规则、状态变化、数据恢复及关键异常。

开发过程中自主处理常规技术问题。若需要改变已确认的产品行为、扩大阶段范围或变更重要契约，先说明影响并更新方案，相关改动经用户确认后实施；不受影响的工作继续推进。

### 4.4 交付用户验收

开发代理提供可运行版本、启动或访问方式，以及阶段文档中的手工验收步骤。交付时说明已实现范围、自动验证结果和已知限制，确保用户可以独立完成测试。

用户重点测试交互体验、实际输入材料和预期业务结果。自动验证由开发代理负责；用户无需重复检查内部代码逻辑，也无需从聊天记录中整理测试步骤。

### 4.5 反馈与修正

开发代理将反馈区分为实现缺陷、需求调整和新增范围，并在当前阶段文档记录处理结论。

实现缺陷修复后执行必要验证并提供复测步骤；需求调整更新所属长期规范并确认影响；新增范围由用户决定纳入当前阶段还是后续交付。每次实际文件编辑后仍按 Git 规则询问是否提交。

### 4.6 完成阶段并推进

阶段完成需要同时满足：已确认范围完成、必要自动验证通过、用户验收通过，以及未解决问题已经关闭或由用户明确接受其影响和后续安排。

开发代理补全交付记录、用户验收结论和对应提交，更新整体交付计划的阶段状态，然后准备下一阶段。应用验收通过不代表已经提交；尚未提交的改动仍需单独确认。

## 5 变更与追溯

- 新决策先更新唯一所属的长期规范，当前阶段引用更新后的内容。
- 已完成阶段保留当时的验证结果和提交依据，不用后续规则覆盖历史结论。
- 后续发现的问题在当前处理阶段记录，并引用受影响的历史交付。
- 当前规范与历史交付不一致时，说明变更依据及生效范围；历史记录不自动视为符合新标准。
- README 提供文档导航，交付计划汇总范围、状态及长期验收标准，详细任务及验证结果留在阶段文档。

## 6 协作分工

开发代理负责提出方案、维护文档、实现代码、完成自动验证、提供可运行交付并处理反馈；用户负责关键方案审核、产品取舍、应用测试与验收确认。

每次交付围绕当前阶段文档及有变化的规范展开。提交、合并和推送的具体规则统一引用 AGENTS.md，不在本文重复维护。
